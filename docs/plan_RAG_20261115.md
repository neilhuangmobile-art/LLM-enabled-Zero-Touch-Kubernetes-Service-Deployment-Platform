## 一、結論先講

1. **RAG 要解決的核心問題是「系統不認識軟體」**：盲測情境題 0/8、r3 的 ghost 題同時錯了連接埠（給 80，實際 2368）和保存路徑。補這塊知識，比調檢索參數重要得多。
2. **軟體知識可以自動從官方來源建立**：Docker Hub 映像檔設定裡有每個版本的連接埠與資料目錄（✅ 已實測讀出），官方說明文件有必要的環境變數。不必人工抄寫，也能隨版本更新。
3. **檢索結果直接是可用的值**，不是一段文字；分數不夠就不給答案，交給代理反問。
4. 其餘依規劃稿的順序逐步做，**每一步先量測、有進步才保留**；強化學習調參放最後，且要先贏過簡單的網格搜尋才採用。

## 三、目標與設計原則

RAG 服務三個呼叫者：**推理代理補欄位（本次重點）**、一般問答、Healer 診斷（之後）。

| 原則 | 理由 |
|---|---|
| 結構化知識優先，檢索結果就是值 | 少一層「從文字抽答案」的錯誤；值可以被程式驗證 |
| 能從權威來源自動取得的，不靠人寫、不靠模型猜 | 連接埠、資料目錄有官方設定可讀；人工抄寫會過時或抄錯 |
| 分數不夠就放棄 | 給錯答案比反問更糟（11/07 前自動補 nginx 的教訓） |
| 一次只改一處、先量測 | Best Practices in RAG 的逐步法；10/08 混合檢索實測反而退步的教訓 |
| 部署知識庫唯讀、與使用者上傳分開 | 避免知識庫被汙染（PoisonedRAG，USENIX Security 2025） |
| 評估資料永遠不進知識庫，並用程式檢查 | 避免分數虛高 |

## 四、架構

```
呼叫者（推理代理／問答／Healer）
   │ retrieve_for_field  retrieve_requirements  retrieve_knowledge
   ▼
路由（rag/router.py）
   依「最終判定的動作」＋「要補的欄位」決定查哪個庫；資訊完整的部署不查
   ▼
┌───────────────┬──────────────────┬──────────────────┬───────────────┐
│ C1 軟體目錄     │ C2 需求通則＋情境範例 │ C3 K8s 知識文件     │ C4 疑難排解     │
│ 結構化、唯讀    │ 結構化、唯讀         │ 段落               │ 症狀→原因→修法  │
└───────────────┴──────────────────┴──────────────────┴───────────────┘
   ▼
檢索：BGE-M3 向量（對照：修正中文分詞後的 BM25）
   ▼
後處理：門檻 → 去重（同一軟體留一筆）→ 依版本補值 → CRAG 判斷（分數偏低改查他庫或放棄）
   ▼
輸出：候選值＋依據＋分數＋來源（C1、C2）／段落＋來源（C3、C4）
```

### C1 軟體目錄（最重要，半自動建立）

```yaml
- id: ghost
  image: ghost
  default_tag: "5"
  scenarios: ["個人部落格", "寫文章發表", "日記網站", "團隊官方網誌"]   # 人寫：給向量檢索用的情境描述
  standalone: true                     # 單一容器可運作（系統一次只部署一個服務）
  versions:
    "5": {ports: [2368], volumes: ["/var/lib/ghost/content"]}          # 程式從 Docker Hub 設定讀出
  env_required: []                     # 程式從 docker-library/docs 擷取，人工確認
  env_common: {url: "http://<host>:2368"}
  resources: {memory: 256Mi, cpu: 250m}
  sources: ["registry:library/ghost:5", "https://github.com/docker-library/docs/tree/master/ghost"]
```

- **自動部分**（`rag/textbook/build_catalog.py`）：從 Docker Hub 設定讀連接埠與資料目錄（依版本）；從 docker-library/docs 的 `content.md` 擷取環境變數名稱與「必要」標記，人工確認後寫入。
- **人工部分**：情境描述、`standalone`、常見資源量。
- **單一容器優先**：系統一次只能部署一個服務（實驗中「一句話兩個服務」失敗 3 次）。像 wikijs 預設要另一個資料庫，目錄裡要標 `standalone: false`，並列出單一容器的替代做法（例如改用 sqlite 的設定），檢索時優先回傳可獨立運作的選項。
- 初版約 40 個軟體，涵蓋實驗出現過的所有類型。

### C2 需求通則與情境範例

- **需求通則**（結構化）：「資料不能不見／重開機不能消失」→ 保存空間；「每天半夜／每週日」→ 定時工作；「不用讓人連／背景跑」→ 不對外；「設密碼」→ 環境變數。每條附對應的 K8s 寫法在 C3 的段落編號。
- **情境範例**：由 C1 的情境描述請 Gemini 改寫成新手說法，每句附正確中間 JSON；人工抽查後放入。與原本 1,883 筆樣板句分開存放。

### C3、C4

- C3：現有 16 份文件＋kubernetes/website 選錄（保存空間、定時工作、環境變數與 Secret、健康檢查、Service 類型），段落前加文件與章節標題（Contextual Retrieval）。
- C4：從 `common_errors.md`、`troubleshooting_advanced.md`、`pod_status_explained.md` 拆成「症狀 → 原因 → 修法」條目。

### 路由表

| 最終判定的動作 | 查哪裡 |
|---|---|
| 部署，且六個基礎欄位齊全、無額外需求 | 不查（快路徑） |
| 部署，缺欄位或有額外需求 | C1（依欄位）＋C2 |
| 情境部署 | C1＋C2 |
| 一般問答（概念） | C3 |
| 錯誤排除、Healer | C4（＋即時日誌，由呼叫者提供） |
| 狀態查詢、擴縮、刪除、排程等操作 | 不查 |
| 平台使用問題 | 使用說明文件 |

### 資料

### 指標

| 指標 | 計算 |
|---|---|
| 映像檔命中率 | 前 1／前 3 名候選在題目的可接受清單內 |
| 連接埠、資料路徑正確率 | 與 C1 的權威值比對 |
| 額外需求召回率 | 題目列出的額外需求被找到幾項 |

## 六、介面（給組員）

```python
retrieve_for_field(query: str, field: str, top_k: int = 3, version: str | None = None) -> list[dict]
# field：image、port、volume、env、memory、cpu、replicas（只給常見範圍）；app_name 不由 RAG 決定
# [{"value": "ghost:5", "field": "image", "score": 0.81,
#   "evidence": "軟體目錄 ghost：個人部落格、日記網站", "source": "catalog#ghost",
#   "related": {"port": 2368, "volume": "/var/lib/ghost/content", "standalone": true}}]
# 分數低於門檻 → []（代理改為反問）

retrieve_requirements(query: str, top_k: int = 5) -> list[dict]
# [{"need": "persistent_storage", "score": 0.77, "evidence": "資料不能不見 → 保存空間", "k8s_ref": "C3#storage-pvc"}]

retrieve_knowledge(query: str, kind: str = "concept", top_k: int = 3) -> list[dict]   # 問答、Healer
```

- 先交付**假實作**（固定回傳），組員立即可用；真實作完成後替換，介面不變。
- 舊的 `retrieve()`、`retrieve_deploy_examples()` 保留，現有流程不受影響。
- 每個回傳值都有 `evidence` 與 `source`，確認卡可以標示「建議值，依據：…」。

## 八、顯存與效能

- BGE-M3 目前在 GPU。若組員的推理模型需要空間，可改設 `RAG_EMBED_DEVICE=cpu` 釋出約 1～2GB（10/08 實測 CPU 約 90 毫秒一次）；要不要改，等推理模型選定後一起量測。
- C1 查詢以結構化資料為主，檢索量小，延遲目標每次 200 毫秒內。
