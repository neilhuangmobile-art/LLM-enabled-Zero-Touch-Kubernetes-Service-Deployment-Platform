## 一、目的與依據

11/06～08 與 Claude Code 的對照實驗（`docs/bench_record/`、GitHub issue #1）顯示：

| 指標 | ZeroTouch | Claude Code |
|---|---|---|
| 第三方出題盲測通過率 | 36.7% | 75.0% |
| 情境題（只描述情境、沒說軟體） | 0/8 | 6/8 |
| 資料庫、背景程式、英文 | 0/8、0/6、0/6 | 5/8、1/6、6/6 |
| 部署回應時間（中位數） | 1.9 秒 | 45.4 秒 |

失敗的根本原因：意圖判斷把部署需求當成問答（30 次，11/08 已修）、情境題沒有軟體建議（19 次）、規格欄位不夠導致使用者講的保存資料、排程、指令被丟掉（28 次）。新架構要解決後兩者，同時**不能犧牲簡單需求的速度**。

## 三、整體流程

```
使用者輸入
 → Gemini：意圖判斷＋正規化（一次呼叫），輸出中間 JSON
 → 分流判斷（程式）：
     六個基礎欄位齊全、沒有額外欄位、不是情境描述 → 快路徑（現有流程，約 2 秒）
     否則 → 新架構
 → 新架構：
     推理代理：補空缺（RAG 找最接近的常見答案）、寫額外欄位
     缺漏檢查（程式為主）：原句提到的東西有沒有進 JSON → 沒有就交回推理代理（最多 2 次）
     空缺檢查（程式）：基礎欄位有沒有空 → 映像檔、名稱不能猜，一定反問
     格式與負荷檢查（程式）：JSON 結構、K8s 格式定義、容量 → 錯誤訊息回饋推理代理
 → 部署確認卡（標示哪些是建議值，使用者可修改）
 → 現有防護全部保留：參數查證、三方審查、政策驗證、試跑驗證、Git 紀錄 → 部署
```

分流判斷完全用程式，不呼叫模型，所以簡單需求維持現在的速度。

## 四、推理代理的模型

### 顯存現況（11/15 實測，AMD RX 9060 XT 16GB）

Model Server 目前載入 3B 與 1.5B（皆 bf16），**已用 8.6GB，剩約 7GB**；embedding 模型 BGE-M3 跑在 CPU。

| 推理模型（4-bit 權重估算） | 權重約 | 加上現有 8.6GB | 結論 |
|---|---|---|---|
| 7～8B（Qwen2.5-7B、Qwen3-8B） | 約 5GB | 約 13.6GB | 放得下，KV cache 剩約 2GB，需實測 |
| 14B（Qwen2.5-14B、Qwen3-14B） | 約 8～9GB | 超過 16GB | 放不下，除非卸下 3B |
| 14B，並卸下 3B | 約 9GB | 約 12GB | 放得下；3B 的工作改由推理模型或 Gemini 承擔 |

3B 現在的角色只剩「Gemini 與規則都解析不出來時的後備」，11/08 後意圖判斷也改由 Gemini 優先。因此**卸下 3B、改由推理模型同時負責後備解析**是可行選項。

### 兩台機器的差異（重要）

| | 這台（AMD RX 9060 XT） | 學校那台（NVIDIA RTX 5080 Laptop 16GB） |
|---|---|---|
| 4-bit 方式 | bitsandbytes 不能用；需改用 GGUF（llama.cpp）或 AWQ／GPTQ（ROCm 支援度需實測） | bitsandbytes、AWQ、vLLM 皆可 |
| 建議引擎 | llama.cpp（GGUF） | vLLM（連續批次、前綴快取、JSON 結構約束輸出） |

兩台的推論方式不同，模型伺服器要做成可切換的後端，代理只呼叫統一介面。

### 建議：先量測再決定，候選四個

| 候選 | 理由 |
|---|---|
| Qwen2.5-7B-Instruct（4-bit） | 與現有 Qwen2.5 系列提示格式相容，放得下不用卸 3B |
| Qwen3-8B（4-bit，關閉思考模式） | 較新，推理較強；思考模式會大幅增加延遲，代理任務應關閉 |
| Qwen2.5-14B-Instruct（4-bit，卸下 3B） | 能力最強的可行選項 |
| Gemini（不佔顯存）作為對照基準 | 已在使用；若本機模型不比它好，本機模型的價值只剩離線可用 |

量測方式：用開發集（見第八節）比較**欄位填寫正確率、反問是否恰當、延遲、顯存**，選分數與延遲取捨最好者。推理代理一次部署可能呼叫 2～4 次，延遲目標：新架構整體 **10 秒內**，並在畫面顯示進行到哪一步。

## 五、中間 JSON 規格（兩條線共用）

```json
{
  "schema_version": 1,
  "source_text": "使用者原句",
  "intent": "deploy",
  "route": "fast | agent",
  "base": {
    "app_name": {"value": "wiki", "from": "user | inferred | rag | default"},
    "image":    {"value": "requarks/wiki:2", "from": "rag", "evidence": "軟體目錄：wiki"},
    "replicas": {"value": 2, "from": "inferred", "evidence": "15 人同時使用"},
    "port":     {"value": 3000, "from": "rag"},
    "memory":   {"value": "512Mi", "from": "default"},
    "cpu":      {"value": "250m", "from": "default"}
  },
  "extra": [
    {"path": "spec.template.spec.volumes[0]", "value": {"...": "..."}, "reason": "使用者說資料不能消失", "from": "inferred"}
  ],
  "missing": ["image"],
  "ask": ["要用哪一套 wiki 軟體？"]
}
```

- 每個值記錄來源，確認卡才能標示「建議值」。
- **額外欄位**：模型自行產生「K8s 欄位路徑＋值」，但由**程式**套用到 YAML，並用 K8s 官方格式定義與試跑驗證檢查；不合法的退回推理代理。危險設定（特權、主機路徑）照舊被安全代理擋下。這保留模型的彈性，又不讓它直接寫 YAML。
- **不能猜的欄位**：`image`、`app_name` 若原句與 RAG 都沒有足夠依據，一定反問（避免重演自動補 nginx 的錯誤）。

## 六、RAG 改版（黃柏碩負責）

### 給推理代理的介面

```python
retrieve_for_field(query: str, field: str, top_k: int = 3) -> list[dict]
# 回傳 [{"value": "requarks/wiki:2", "text": "依據的段落", "score": 0.82, "source": "textbook/software.yaml"}]
# 分數低於門檻時回傳空清單，推理代理就改為反問
```

介面先定下來並附一個假的實作（固定回傳），組員可以立即用假的開發，RAG 完成後直接替換。

### 步驟（一次只改一處，有進步才保留）

1. **建基準**：沒 RAG／現在的 RAG／故意給錯文件三組，用開發集量欄位正確率。
2. **經驗教科書**（新增資料來源）：軟體目錄（情境 → 建議軟體，例如 wiki → wikijs、程式碼託管 → gitea、檔案分享 → filebrowser、部落格 → ghost）、每個映像檔的監聽連接埠、資料路徑、必要環境變數；名稱別名（mongodb → mongo）。只放歸納的通則，不放盲測原句。
3. **部署範例改用 embedding**：目前部署範例 1,802 筆仍是 TF-IDF（中文沒有斷詞），改用 BGE-M3（問答那邊已採用，24 題 Recall@3 95.8%）。K8s 文本多數詞只出現一兩次，TF-IDF 難以比對語意相近的需求。
4. **依問題類型分流檢索**：直接用現有的意圖分類當路由，部署資訊完整的不查。
5. **門檻與取幾筆**：用開發集畫「門檻 vs 正確率」曲線決定，不再用憑經驗定的 0.3。
6. 量測後才決定：混合檢索與重新排序（10/08 實測反而退步、延遲 110 倍，資料變大後重測）、Qwen3-Embedding。

## 七、檢查代理的設計原則

依 Huang et al.（ICLR 2024）：沒有外部回饋時，模型自我修正常常無效。所以檢查以程式為主、模型為輔。

| 檢查 | 主要方式 | 模型的角色 |
|---|---|---|
| 缺漏 | 程式比對原句中的映像檔、數字、名稱、關鍵需求詞是否進 JSON | 只判斷程式抓不到的語意 |
| 空缺 | 程式逐一檢查六個基礎欄位 | 無 |
| 格式與負荷 | JSON 結構、K8s 格式定義、容量計算、試跑驗證 | 無；錯誤訊息回饋推理代理 |
| 推理結果第二意見 | 不同家族模型（Gemini）或同模型取樣 3 次投票 | 不一致就在確認卡上交給使用者 |

補填重試：同一欄位最多 2 次，仍不行就反問。

## 八、評估與驗收

| 資料 | 用途 | 規則 |
|---|---|---|
| 開發集（Gemini 新出，全部情境題，分難易） | 調 RAG 門檻、選推理模型、調提示 | 可以閱讀，但不能當驗收證據 |
| 盲測集（Gemini 另出一批＋現有 r4 15 題） | 最後驗收 | 開發端不讀內容 |

驗收：盲測通過率與 36.7% 比較（附 95% 信賴區間）；簡單需求延遲不得明顯高於 1.9 秒；新架構延遲 10 秒內。

## 九、時程與合併

1. RAG 線：介面規格與假實作（先給組員）→ 基準量測 → 教科書 → embedding → 門檻調整。
2. 組員線：中間 JSON → 分流 → 推理代理 → 檢查代理 → 確認卡標示。
3. 推理模型量測（兩條線都需要，建議組員在 NVIDIA 那台、黃柏碩在 AMD 這台各測一次）。
4. 合併：先合 RAG 線（介面已固定），再合多代理線；修 CI；全部測試通過；跑盲測。
5. 文件：CHANGELOG、`docs/security_review.md`（額外欄位由模型產生的風險與防護）。

## 十、風險

| 風險 | 對策 |
|---|---|
| 新架構太慢 | 快路徑保留；檢查用程式；量測延遲是實作後第一件事 |
| 顯存不夠 | 依第四節量測；必要時卸下 3B |
| AMD 跑不了 4-bit | 改用 GGUF；或推理代理在這台改用 Gemini、在 NVIDIA 那台用本機模型 |
| 額外欄位寫出危險或錯誤設定 | 程式套用＋格式驗證＋試跑驗證＋安全代理，四層防護 |
| 用開發集調出來的效果在盲測不成立 | 開發集與盲測集分開，盲測內容不讀 |
