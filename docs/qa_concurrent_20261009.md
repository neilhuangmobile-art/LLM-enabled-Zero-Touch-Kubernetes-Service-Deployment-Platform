# 兩人同時使用測試報告（客戶自帶叢集模式）

測試日期：2026-10-09
測試腳本：`qa_concurrent_users.py`
原始資料：
- 第二輪（正式結果）：`docs/qa_concurrent_20261009.jsonl`、`docs/qa_concurrent_20261009_summary.json`
- 第一輪（抓到錯誤的那一次，保留供對照）：`docs/qa_concurrent_20261009_run1.*`

## 測試目的

確認兩個客戶在同一時間使用平台時：

1. 功能都正常：Chat 問答、意圖判斷、自然語言部署解析、部署、擴縮、刪除。
2. 兩人的資料完全隔離：看不到對方的服務，Chat 也不會講到對方的服務。
3. 同時使用會不會明顯變慢。

## 測試環境

- 網站：透過 Tailscale Funnel 對外開放（`https://user.tail4c2fd2.ts.net`），所有請求都走外網網址。
- 兩個測試帳號各自完成「同意書 → 貼指令 → 連線檢查」，分別使用兩個獨立的客戶 namespace。
- 兩個客戶叢集都在同一台電腦的 Docker Desktop 上（限制見最後一節）。
- Model Server：Qwen2.5-3B 與 1.5B，AMD RX 9060 XT，bf16。

## 測試流程

先由帳號 A 單獨問 3 題 Chat，作為基準。接著兩個帳號在同一時刻開始，各自跑完以下流程：

| 步驟 | 判定通過的規則 |
|---|---|
| Chat 問答 3 題 | HTTP 成功且回覆非空 |
| 意圖判斷 | 判斷結果是 deploy |
| 自然語言部署解析 | app_name、副本數一致，**映像檔完全等於 nginx:1.27** |
| 部署 | 已 commit 到客戶的 repo |
| 等叢集同步 | 叢集上 2/2 ready（180 秒內） |
| 隔離檢查 | Deployments 清單裡沒有對方的服務 |
| 擴縮到 3 | 已 commit；叢集上 3/3 ready |
| 問自己服務的狀態 | 有回覆，而且沒有提到對方的服務 |
| 刪除 | 已 commit；服務從叢集消失 |

## 結果

| | 第一輪 | 第二輪（修正後） |
|---|---|---|
| 題數 | 29 | 29 |
| 通過 | 29（**判定規則太寬鬆，藏了一個錯誤**） | **29**（嚴格規則） |
| 隔離檢查（4 題） | 全過 | 全過 |
| 整個流程耗時 | 243 秒 | 160 秒 |

### 第一輪抓到的錯誤

帳號 B 輸入「部署 2 個 nginx:1.27」，解析結果卻是 `nginx:latest`。第一輪的判定規則只檢查映像檔名稱裡「有沒有 nginx」，所以把這個錯誤算成通過。

追查後的結果：

- 同樣的輸入**單獨送 4 次全對**；**兩人同時送 4 輪（8 次）錯了 5 次**。
- 原因不是兩個人的資料互相干擾，而是兩人同時送出時，翻譯層 Gemini 回傳 429（額度用完）或 503（過載），系統退回本機的備援解析器。
- 這個備援解析器處理中文輸入有缺陷，**會丟掉版本號，「部署 2 個 redis:7.2」甚至會變成 nginx:latest**，也就是使用者要 redis，卻部署了 nginx。

修正（commit `a0b6eab`）：補上兩條更可靠的映像檔比對規則，新增 7 個回歸測試，並把 QA 判定改成映像檔必須完全一致。修正後第二輪兩個帳號都正確解析出 `nginx:1.27`。

### 各步驟延遲（第二輪，兩人同時）

| 步驟 | 平均 | 最慢 |
|---|---|---|
| Chat 問答 | 10.7 秒 | 16.0 秒 |
| 部署解析 | 4.8 秒 | 5.1 秒 |
| 部署 commit | 5.2 秒 | 5.4 秒 |
| 部署到叢集生效 | 22.5 秒 | 25.0 秒 |
| 擴縮到叢集生效 | 32.5 秒 | 40.0 秒 |
| 問服務狀態（接地問答） | 13.2 秒 | 13.8 秒 |
| 刪除到叢集生效 | 30.0 秒 | 45.0 秒 |

所有「已送出」類的操作（commit）都在 6 秒內完成。「到叢集生效」取決於 Flux 每 30 秒的同步週期，所以落在 20～45 秒。

### 關於「同時使用會不會變慢」

| | 第一輪 | 第二輪 |
|---|---|---|
| 單人 Chat 平均（3 題） | 25.6 秒 | 19.7 秒 |
| 兩人同時 Chat 平均（6 題） | 27.8 秒 | 10.7 秒 |

**這組數據不能用來下結論**：第二輪「兩人同時」反而比「單人」快，第一輪則是慢一點。Chat 的時間大部分花在等外部的 Gemini API，Gemini 的回應速度起伏很大，基準組又只有 3 題，誤差遠大於「同時使用」本身造成的影響。

能確定的只有一點：**兩人同時使用沒有造成明顯變慢，也沒有任何請求失敗**。要量化 Model Server 一次只處理一個請求的排隊成本，需要換一種測試：不經過 Gemini，直接對 Model Server 送請求，並且加大樣本數。

## 測試過程中一起發現並修好的問題

| 問題 | 發現方式 | 修正 |
|---|---|---|
| Gemini 失敗時，中文部署指令會裝錯映像檔 | 本測試第一輪 | 見上文 |
| 重跑安裝指令後回報器被拒（401），叢集看起來離線 | 準備第二個帳號時 | 回報器 Pod 範本加雜湊，自動重啟 |
| 用 http://127.0.0.1 測試會一直未登入 | 重現錯誤時 | 不是系統問題：設定對外網址後 cookie 只走 https，瀏覽器不受影響 |

## 限制

- 兩個「客戶叢集」在同一台電腦上，還沒有用另一台電腦、另一個網路實測，例如學校的筆電。
- 每個步驟只有 2 個樣本（兩個帳號各 1 次），延遲數字只能當參考。
- 只測兩人同時使用；更多人同時使用時，Gemini 額度和 Model Server 排隊的影響會更明顯，需要另外做負載測試。
