## 評估過程發現並修正的問題

第一次跑（`healer_new2.jsonl`）也是 35/35，但 slow-start 的紀錄有異常：驗證判定「沒修好」並退回了，服務最後卻是健康的。查出兩個 bug：

1. **驗證誤判**：startupProbe 在程式啟動期間本來就會失敗幾次（事件 `Unhealthy: Startup probe failed`），驗證把它當成「修完又壞」。修正：啟動探針的失敗事件不算。真的啟動不了，Pod 會被重啟，由「修復後重啟次數」抓到。
2. **退回沒退乾淨**：退回用合併式 patch，拿不掉修復時新增的欄位，startupProbe 留了下來。服務最後健康，其實是因為退回沒成功。修正：退回一律整個物件取代（帶 resourceVersion，中間有人改過就會失敗，不會蓋掉別人的修改）。

這兩個 bug 在階段 1 就存在，只是原本的修法都不會新增欄位，所以之前沒有發現。兩個都補了回歸測試（`tests/test_healer_verify.py`），最終版重跑後 slow-start 驗證通過，沒有退回。

## 沒有用真叢集評估的部分（只有單元測試）

- **客戶叢集的驗證與退回**（`cluster/remote_verify.py`）：需要真的客戶叢集、Flux、回報器。用回報器格式的假資料測了同步、健康 90 秒、逾時退回、使用者中間改過就不退回（`tests/test_remote_verify.py`）。
- **階段 4 診斷品質**（log 去重、處理手冊、證據引用、過去修法）：只影響送給模型的內容。評估沒有呼叫模型（`--llm` 才會），所以這部分只有單元測試（`tests/test_healer_logsift.py`、`tests/test_healer_evidence.py`）。模型的提示詞改了，**model server 要重啟才會生效**，而且還沒用真的模型測過「會不會照格式給 evidence」。
- **被驅逐（evicted）**：在單節點上很難安全地製造，只有單元測試。
- **限流狀態還原**：網站重啟後從事件紀錄重建，只有單元測試。
- **定時執行的 podFailurePolicy**：單元測試，加上 API server 試跑（`kubectl apply --dry-run=server`）接受新樣板。

## 限制

- **題目是調整 Healer 的人出的**（開發題組），不能當最終成績。盲測題請照 `experiments/healer_eval/BLIND_GUIDE.md` 由組員出，版本凍結後只跑一次。
- 每版只跑一次。新增的 13 題只有新版的結果，舊版沒有這些功能，不做配對比較。
- 評估時縮短了「一直沒就緒」的門檻（1 分鐘，正式是 15 分鐘）。

## 重跑方式

```bash
python experiments/healer_eval/run_eval.py --tag new3 --run n5
```

大約 10 分鐘：35 題同時跑，每題用自己的 namespace，結束後自動刪除。
