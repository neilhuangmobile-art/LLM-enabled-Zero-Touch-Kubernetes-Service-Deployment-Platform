# 情境部署準確率：實驗結果與柏碩版本比較（2026-11-24）

- **作者**：陳冠穎（學校 RTX 5080 電腦）。
- **比較對象**：柏碩 11-20 的版本（`6666a36`：選軟體信心度、軟體目錄 76 套、盲測 50.6%）。
- 細節與過程：
  - `docs/bench_record/2026-11-23_反問與選軟體改善.md`
  - `CHANGELOG.md` 2026-11-23 各節
  - `docs/security_review.md` 第 69 節

## 一句話結論

- **沒看過的題目**：同一份題目上，柏碩那套設定（本地正規化）是 61.3%，我們的版本是 75.0%。
- **開發題組 claude**：66.0% → 78.6%。
- **改進來源**：
  - 「少問不該問的」：Gemini 判斷使用者有沒有講清楚要哪一類軟體。
  - 「採用 Gemini 建議的軟體」。
  - 補知識表。
  - 資源改用「知識表建議值高一格」。
- **還沒解決**：「該問卻沒問」仍偏多；極短的句子準確率會掉。

## 名詞

| 名詞 | 意思 |
|---|---|
| 整張全對 | 不該反問的題目：映像檔、副本數、port、記憶體、CPU 全部在範圍內，而且沒有多問。和柏碩的評分完全相同（`run_pipeline_dev.py`，映像檔比對最後一段名稱）。 |

## 二、沒看過的題目（獨立驗證題組 holdout，100 題）

- **出題方式**：另開一個看不到程式、看不到開發題組的 Claude，照同一份規則出題。
- **規則**：該問＝沒講是哪一類軟體、自己的程式沒講語言、矛盾會改變要裝哪一套。
- 使用者抽查後鎖定，三種設定各跑一次，只看統計。

| 設定 | 整張全對（/80） | 該問有問到（/20） | 不該問卻問了 |
|---|---|---|---|
| 柏碩版設定（本地正規化） | 49（61.3%） | 11 | 11 |
| 網站改動前（Gemini 正規化） | 56（70.0%） | 11 | 11 |
| **我們的版本**（反問改善＋採用建議） | **60（75.0%）** | **13** | **1** |

- **柏碩版設定 → 我們的版本**：多對 11、少對 0，p=0.001。
- **網站改動前 → 我們的版本**：多對 5、少對 1，p=0.22（題數太少，還不確定）。

**注意**：

## 四、為什麼 scenario 組特別低

- **錯在資源大小**：只要 CPU 和記憶體對了，scenario 組整張全對就會從 75 升到 108/157。
- **錨定效應**：推理 prompt 範本寫著 `"cpu": "<e.g. 250m>"`，系統有 98/157 題給 250m，就是照抄範本的數字。模型估數字時會被 prompt 裡出現的數字拉走。
  - 論文：SynAnchors arXiv 2505.15392、Anchors in the Machine arXiv 2511.05766。
- **兩組題目的資源標準相反**：

  | 題組 | 出題者 | CPU 下限多在 |
  |---|---|---|
  | scenario | Gemini | 200～500m |
  | claude | Claude | 100m |

  所以一律調高行不通：固定 500m 時，claude 組 202 → 186。
- **解法：資源刻度**（`PIPELINE_SIZE_TIER=floor`）
  - 數字不讓模型直接寫，改用知識表每套軟體的建議值，往上一格。
  - 刻度：CPU 50／100／250／500／1000m，記憶體 64／128／256／512Mi／1Gi。
  - 只往上調，不調小。
  - 這是 LASER（arXiv 2512.19701）的分工：模型判斷類別，數字交給查表和規則。
- **為什麼用刻度、不用倍數**：模擬時「建議值 ×2」看起來最好，但 ×1.75、×2.25 就大幅變差。×2 只是剛好把 250m 變成 500m、256Mi 變成 512Mi，碰到標準答案的邊界。所以改用刻度。
- **上限**：scenario 組就算資源全對，也只到 68.8%。這組要到 75% 不實際，剩下的是軟體和 port 錯誤。

## 五、試過但沒採用

| 做法 | 結果 | 原因 |
|---|---|---|
| 本地判斷「講清楚了沒」，和 Gemini 合併（`PIPELINE_CLARITY_COMBINE=or`） | claude 195 → 192 | 多問變多 |
| Gemini 再獨立判斷一次（`PIPELINE_CLARITY_CHECK=gemini2`） | claude 201 → 170、scenario 75 → 66（都 p<0.01） | 每多問到 1 題該問的，約多錯 3 題 |
| 資源一律提高下限（CPU 500m、記憶體 512Mi） | 兩組都變差 | 兩組標準相反 |
| 建議值 ×2 | 看起來最好，但倍數一偏就崩 | 只是碰巧落在標準答案的邊界 |

## 七、怎麼重現

```bash
# 我們的版本（Gemini 正規化走快取；第一次跑要 --gemini --max-gemini-calls N）
PIPELINE_CLARITY=on PIPELINE_CLARITY_LO=0.1 PIPELINE_CLARITY_HI=0.6 PIPELINE_TRUST_SUGGEST=1 PIPELINE_SIZE_TIER=floor \
  python experiments/model_select/reason/run_pipeline_dev.py --set claude --tag 我的版本 \
  --gemini-cache experiments/model_select/reason/results/gemini_cache_claude_clarity_v2.jsonl
# 逐題比較
python experiments/model_select/reason/run_pipeline_dev.py --set claude --compare cuda_school 我的版本
```

- 新增的題組：`--set s40`、`--set perturb`。perturb 的標準答案沿用原題。
- 注意：`.env` 的開關會被評估程式讀到。跑「柏碩版設定」對照時，要明確設 `PIPELINE_CLARITY=off PIPELINE_TRUST_SUGGEST=0`。
