# PROMPTx-RAG：依情境挑選檢索策略的實驗報告

2026-11-15。方法參考 Khan et al., *PROMPTx-PE*, CMC 2026, 87(2)（張賢宗教授研究團隊，CC BY 4.0），
本報告只引用其方法，不引用其數據。

## 摘要

以 PROMPTx-PE 的多目標獎勵（準確 0.4、穩健 0.4、效率 0.2）評估欄位檢索的 10 種策略，並比較
「固定最佳策略」與 5 種依句子情境逐句挑策略的學習方法（LinUCB、Thompson 抽樣、DQN、自動調權重、自動退回）。
題目 419 題（Gemini 出題 157、Claude 出題 262），其中 397 題另有 4 種改寫（錯字、極短、囉嗦、中英夾雜）。

1. **逐句挑策略的學習方法都沒有贏過固定最佳策略**（5 折 × 3 種子，Nadeau–Bengio 修正 t 檢定，p 皆 > 0.07），
   跨出題者測試也沒有一致較好。逐句理想上限（oracle）比固定最佳高 0.093，表示策略之間確實互補，
   但現有 8 個句子特徵預測不出哪一題該用哪個策略。依事先寫死的採用規則，**不採用**。
2. **固定最佳策略是 `ext_d03_mr`**（範本版擴充目錄、人工與擴充分開索引、擴充需高出 0.03 才進前排、每句描述各自建索引）。
   相對於現行正式版，總分 +0.0116（逐題 bootstrap 95% CI [0.0018, 0.0216]），前 3 名命中 66.6% → 68.7%，
   兩個出題來源都提升。**但逐項 McNemar 經 Holm 校正後都不顯著**，且這個組合是看過結果才提出的，
   屬探索性結論，需用盲測集確認一次才改預設。
3. 11/15「擴充目錄會變差」的結論只適用於 Gemini 撰寫的描述與合併索引。改用不經 LLM 的範本描述、
   人工與擴充分開索引後，擴充不再變差（兩個出題來源都 +1.9～2.3 個百分點），支持「寫法偏差」的診斷。
4. 本機 Qwen 3B 改寫查詢是最穩健的策略（四種改寫裡最差的命中 47.9%，中英夾雜句 +8.6 個百分點，Holm p < 0.001），
   但每句多 1.2 秒，在 0.2 的效率權重下總分最低。重排序（bge-reranker）準確度反而下降且每句 8 秒。

## 1. 方法

### 1.1 對應 PROMPTx-PE

| PROMPTx-PE | 本實驗 |
|---|---|
| 動作：修改提示 | 每句選一個檢索策略（臂），共 9 個參與學習 + 重排序只跑原句 |
| 情境（式 3） | 句長、英文比例、是否直接寫軟體名、數字數、人工目錄最高分與第 1/2 名分差、擴充減人工分差、需求 BM25 最高分 |
| 獎勵（式 10） | R = 0.4·準確 + 0.4·穩健 + 0.2·效率 |
| 準確 | 0.5·前 3 名命中 + 0.3·第 1 名命中 + 0.2·需求召回 |
| 穩健（式 6，取最差） | 4 種改寫中最差的前 3 名命中 |
| 效率 | 1 − 0.5·log10(延遲 / 50 ms)，截在 [0, 1] |
| 演算法 1（DQN）、式 7（調權重，門檻 0.05）、演算法 2（退回） | `rag/policy.py` 的 dqn、linucb_aw、linucb_rb |

一句查詢只做一次選擇、沒有後續狀態，所以主方法是情境式多臂老虎機（LinUCB、Thompson），DQN 作為論文做法的重現。

### 1.2 題組與防汙染

- Gemini 開發集 `docs/bench_blind/dev_scenario.jsonl`、Claude 開發集 `dev_claude.jsonl`（另開 `claude -p`，
  在空資料夾、不開任何工具，讀不到專案與知識庫）。只取不需反問的題目（反問規則等多代理架構合併後再做）。
- 改寫版本 `dev_perturb.jsonl` 由 Claude 產生，1900 筆，涵蓋 475 題（評估用到 397 題）。
- 防汙染測試 `tests/test_field_retriever.py`（12 項）通過：題目與知識庫無重疊。
- 盲測集未使用。

### 1.3 策略（臂）

| 臂 | 說明 |
|---|---|
| seed_hybrid | **現行正式版**：人工 36 種目錄，向量 + BM25 以 RRF 合併 |
| seed_hybrid_mr | 同上，每句情境描述各自建索引 |
| seed_dense / seed_bm25 | 只用向量 / 只用 BM25 |
| seed_rewrite | 先用本機 Qwen 3B 改寫查詢，再混合檢索 |
| seed_rerank | 混合檢索後 bge-reranker 重排（只跑原句） |
| ext_d03 / ext_d06 | 加入範本版擴充目錄（409 種），分開索引；擴充向量分數高出人工最佳 0.03 / 0.06 才進前排 |
| ext_d03_mr | ext_d03 + 每句描述各自建索引（**事後追加，探索性**） |
| merged_prior | 人工與擴充混在同一索引 + 主流軟體優先 |

只查人工目錄的臂與正式版逐題相同（`strategy_eval.py sanity`：60/60）。

### 1.4 評估

- 5 折交叉驗證 × 3 個種子（依題號雜湊分折），學習方法只用訓練折。
- 學習方法對固定最佳：Nadeau–Bengio 修正重複抽樣 t 檢定（15 個折差）。
- 單一策略對正式版：逐題總分差的 bootstrap 95% CI；前 3 名命中的 McNemar 精確檢定，
  全部 40 個檢定（8 個策略 × 5 種句型）一起做 Holm 校正。
- 跨出題者：Gemini 題訓練 → Claude 題測試，以及反向。
- 採用規則（實驗前寫死在程式）：總分顯著高於固定最佳（p < 0.05）且兩個跨出題者測試都不低於固定最佳。

## 3. 討論

**為什麼學不起來。** oracle 上限高，代表常有「某題只有某個策略答對」的情況，但這些勝負多半取決於句子跟
目錄描述的細節用字，句長、英文比例、分數差這類粗特徵分不出來。可行的下一步是把確認卡回饋（使用者實際選的軟體）
當歷史特徵，這要等多代理架構合併、有線上資料後才能做。

**為什麼擴充這次沒變差。** 11/15 的擴充描述由 Gemini 撰寫，與 Gemini 出的題寫法相近，在 Gemini 開發集上被墊高、
在其他寫法上表現差。這次的擴充描述由中文類別、英文簡介與分類標籤組成，不經 LLM；再加上人工與擴充分開索引，
擴充條目只在明顯更相關時才進前排。兩個出題來源都提升，與寫法偏差的解釋一致。

**權重的影響。** 效率權重 0.2 對 50 ms 以內的策略沒有區分力（效率分數都是 1.0），只懲罰查詢改寫與重排序。
若只看準確與穩健，查詢改寫是最好的策略（0.4·0.619 + 0.4·0.492 = 0.444，正式版 0.419）；
如果之後的多代理流程本來就會呼叫 LLM，可把改寫合併進那一次呼叫，延遲成本就消失，值得在合併後重測。

**限制。**
- ext_d03_mr 是看過結果才提出的組合，ext_d03 與 ext_d06 的門檻也只試了兩個值，存在選擇偏差；
  CI 下限接近 0，逐項檢定校正後不顯著。
- 改寫版本與 Claude 題組都出自 Claude，Gemini 題組的改寫仍是 Claude 寫的，穩健性的分數對 Gemini 題組可能偏低估或高估。
- 22 題沒有改寫版本，穩健項以原句代替（各策略同一批題，不影響比較）。
- 延遲在單機 AMD RX 9060 XT（ROCm）上量測，背景還有其他程序，只適合相對比較。

## 4. 建議

1. **正式版預設先不改。** `ext_d03_mr` 的改善是探索性的，下一步用盲測集測一次（只測正式版與 ext_d03_mr 兩個），
   一致提升才換預設。這一步要使用者確認後才跑。
2. 逐句挑策略（`strategy="auto"`）不實作，因為沒有通過採用規則。
3. 合併後的工作：用確認卡回饋做歷史特徵再試一次策略學習；把查詢改寫併入多代理流程既有的 LLM 呼叫後重測。
4. 中英夾雜是共同弱點：可以考慮在 BM25 前把常見英文詞（database、backup、server 等）對映成中文。
