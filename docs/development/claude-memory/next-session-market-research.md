使用者在 2026-09-15（同一個 session，工作到很晚）收工前明確交代下次回來要做的事，
跟這次的「安全審查」是不同性質的工作（從「系統本身有沒有漏洞」轉向「這個產品在
市場上夠不夠有競爭力、夠不夠貼近使用者需求」），開場可以直接問使用者要先做哪一項，
不用等使用者重新描述一次。

**Why：** 這次 session（含之前）已經把安全/可靠性/測試這條線做得很扎實（多租戶隔離、
prompt injection 雙層防線、healer 真自癒、114+ 測試、CI），使用者現在想往「這個東西
好不好用、有沒有市場價值」這個方向擴展，準備拿去報告/口試，需要有說服力的市場定位
跟創新亮點，不能只靠工程紮實度。

**How to apply（下次要做的四件事）：**

1. **再次以使用者角度嚴厲評判系統**——這是使用者這幾天反覆要求的模式（見
   [[feedback_verify_before_claiming_done]]），不是嘴上稱讚，要挑出具體、可驗證的
   問題。上次評判抓到過 healer 狀態造假的 bug，這種「親自去查程式碼、不是憑印象」
   的評判方式使用者很認可，下次要延續。評判前建議先看一次 `docs/security_review.md`
   全文（現在已經到第 11 節）跟 `CLAUDE.md` 的「進行中工作」歷史，掌握現況再評。

2. **研究這個產業（LLM 驅動的 K8s 零接觸部署平台）的全球痛點**——使用者特別強調
   「甚至是沒被發現的更好」，代表不要只查表面的、大家都知道的痛點（例如「K8s 學習
   曲線陡」），要挖深一點、找還沒被主流工具解決的具體痛點。這需要用 WebSearch/
   WebFetch 查業界資料（部落格、論壇討論、GitHub issue、Reddit/HackerNews 討論串、
   相關新創/工具的定位比較），不是憑內部知識空想。可以對照這個專案已經做的功能
   （自然語言部署、多代理審核、GitOps、自癒），找出「別人也在做但做得不夠好」或
   「大家還沒做」的空隙。

3. **研究使用者希望的友善功能**——跟第 2 項可能有重疊，但角度不同：這個偏向
   UX/易用性層面（不是技術痛點，是「新手/使用者實際想要什麼體驗」），可以參考
   AGENT_RULES.md 已經內化的「對新手絕對友善」原則去延伸，找出還沒做到的友善功能。

4. **Healer 視覺化**——使用者明確講了這是之後想加的功能（不是這次就要做，是先放進
   計畫），具體長什麼樣子還沒定案，下次可以先討論設計方向（例如：即時拓樸圖顯示
   Pod 健康狀態、故障->診斷->修復的時間軸動畫、跟現有 Healer 頁面的關係）。

5. **研究可以加入的創新/創意功能**——跟第 2、3 項一起做，找市場調查時順便留意
   有沒有還沒被想到的功能點子，不限於 Healer 視覺化這一項。

**產出型式的建議**：這類市場調查/評判類的工作，使用者過去偏好「有具體證據、不是
空泛列點」的呈現方式（跟安全審查一樣的風格）——查到的痛點/功能建議最好附上來源
（哪篇文章/討論串/工具），不要憑空生成聽起來合理但查無實據的內容。
