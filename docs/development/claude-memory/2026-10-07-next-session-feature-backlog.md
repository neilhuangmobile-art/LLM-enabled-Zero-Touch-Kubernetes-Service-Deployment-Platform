## 待做項目 1：系統介面動態化（目標是「精緻」，不是單純加特效）

目前大部分畫面是靜態文字，使用者 2026-10-07 兩次都提到要加動畫，明確說目標是讓系統
「更精緻」——不是為了動畫而動畫，是要讓整個產品觀感更專業、更經得起評審/客戶檢視。
**還沒有具體設計**，下次開工時第一步是先盤點現有的動態元素可以沿用什麼——`web_demo.py`
前端已經有 Deploy Console 的「法庭」審查卡片翻牌動畫（security/cost/perf 三張卡依序
翻牌 + 判決 banner，2026-09-07 做的）跟聊天訊息的 spinner/階段性文字，新增動畫前先
確認風格跟這些既有元素一致，不要變成兩種不搭的視覺語言，「精緻」感很大一部分來自
一致性，不是動畫數量多寡。

## 待做項目 2：一句話生成歷史分析報告（有圖有文）+ PDF 下載

使用者要的功能：Chat 輸入一句話，系統依使用者權限範圍內能查到的所有資料（部署、
Healer 事件、GitOps 歷史、資源用量等），生成一份專業報告，**涵蓋從過去到現在的累積
分析，不是只看當下快照**，有文字結論也有圖表，附下載 PDF 的按鈕。

**還沒設計，下次動工前要想清楚的風險點（這次 session 順便想到的，先記下來）**：

1. **幻覈風險比這次 session 修過的任何東西都大**：這次 session 大部分時間都在修
   「模型對短結構化欄位（root_cause 一句話、intent action）幻覈」的問題。一份完整
   的分析報告是**長篇自由文字**，幻覈的空間遠大於一句話的 root_cause——如果報告
   自信地講出一個查無根據的結論（例如「上個月成本上升是因為 X 服務」，但其實查無
   實據），使用者很可能直接把這份報告拿去跟主管/客戶報告，後果比聊天室裡講錯一句話
   嚴重得多。**這個功能一定要延續近失事件可見化的精神**：報告裡「從資料庫查到的硬
   事實」（例如「這個月重啟次數：47 次」）跟「模型對這些事實的解讀/建議」要視覺上
   明確分開標示，不能混在一起變成讀起來都一樣權威的文字。
2. **權限範圍要重用既有的 namespace 隔離，不要另開一條路**：使用者自己有提到「只有
   權限能查詢的資料」，這個直覺是對的——報告產生器呼叫的資料查詢函式，必須走現有
   的 `_user_namespace(session["username"])` 範圍限制，不能另外寫一套繞過既有多租戶
   隔離的查詢邏輯。
3. **報告用的文字生成，可能不該用本地 3B**：這次 research_benchmark.py 量測過，本地
   3B 模型在自由文字生成（/chat）平均要 15 秒、而且品質不確定；一份要拿給別人看的
   「專業報告」，文字品質的要求比聊天室回覆高很多。值得考慮報告的敘述文字這段改走
   Gemini（系統已經有這條管線，只是目前只用在部署請求正規化），本地小模型負責抓
   結構化數據、Gemini 負責把數據組織成讀得順的文字——但要先confirm Gemini 的
   rate limit（每把 key 每分鐘 5 次）夠不夠撐一次完整報告生成會打的請求量。這是
   設計取捨，不是定案，下次動工時要重新評估。
4. **圖表可以直接參考這次 session 做的 research_benchmark 報告**：`research_benchmark.py`
   產生的量化評估報告（Chart.js 畫的準確率/延遲/成長曲線圖表 + PDF 可印出）是現成
   的技術範本，下次做使用者端的分析報告可以直接沿用同一套圖表產生方式，不用重新
   摸索。
5. **可以考慮排程/主動推播版本**：跟 [[2026-10-07-personalization-decision]] 的
   「主動簡報」是同一個方向——報告功能做完之後，可以考慮加一個「每週/每月自動產生」
   的排程版本，不用使用者每次手動開口要，這樣報告本身也變成使用者會想繼續用（續訂）
   的理由之一，不只是被動查詢工具。
6. **加碼想法（2026-10-07 討論，當時漏記，2026-10-08 補上）：成本/風險攔截歸因**。
   把 `agents/orchestrator.py` 的 security/cost/perf 審查判決（block/warn 的結果）
   也存進同一塊資料層，分析報告就能生出「這個月幫你攔下 N 次可能超支的部署，預估
   省下 $X」「你的叢集已經連續 45 天沒有 P0 等級事故」這種用具體數字回答「為什麼
   要繼續付錢」的內容——不是新功能，只是報告產生器多讀一張表（orchestrator 判決
   紀錄），跟上面的 Healer 診斷紀錄/部署歷史是同一塊持久化資料層要存的東西，不是
   另外開發。

## 下次開工順序建議

先做「持久化 Healer 診斷紀錄 + 部署歷史 + orchestrator 審查判決」這個資料層（跟
[[2026-10-07-personalization-decision]] 是同一塊基礎建設，三個功能都要用到），
再做分析報告，動畫排最後（風險最低、跟資料層無關，隨時可以插進去做）。
